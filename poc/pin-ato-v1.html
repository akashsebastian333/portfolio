Cross-site account takeover of a logged-in Pinterest user via the ask.pinterest.com proxy

This page runs from a foreign origin (akashsebastian.com) while the victim is logged in to Pinterest in this browser. With no password and no interaction it re-points the account email at an attacker mailbox, dispatches the password reset there, regenerates and steals the MFA backup codes, and dumps the session inventory. The takeover channel is a fresh Gmail plus-address every run, all delivering to the same attacker inbox: bughunter333333+<random>@gmail.com. Before the email change it also attempts to switch the account's email notifications to “only required”, so the change-of-email alert to the old address is suppressed if Pinterest honours that setting for security mail.

Safety interlock (not part of the exploit)

This hosted copy runs the chain only after a click, so a stray visitor cannot take over a real account by accident. The attacker version runs everything on page load. The requests, targets and ordering below are exactly what the attacker page executes. Both browser classes are handled automatically: with third-party cookies enabled every write rides a hidden iframe and the victim sees nothing; with them blocked the writes are fired as top-level navigations (cookie always attached) which then land the victim on pinterest.com.

Recon: victim identity (JSONP read — also the third-party-cookie oracle)

A script tag pointed at the proxy wraps the response in a callback, so this foreign page can read the account. If this read succeeds, third-party cookies are attached in embedded contexts on this browser and every write below goes through a hidden iframe, completely silent. If it fails (Safari/ITP, Firefox strict, Brave, Chrome third-party-cookie phaseout), the same writes are fired as top-level navigations, which are first-party to ask.pinterest.com and carry the SameSite=None session cookie on every browser.

Silence: strip every optional email notification (CSRF write)

The email-settings tree exposes a global switch, ONLY_REQUIRED — “Control what types of notifications you get (except privacy and account emails)”. A form POST through the proxy runs v3_post_settings_email with the victim's session (verified live: section / option / value fields, no CSRF token) and flips it on, disabling the bulk of the account's email categories in one shot. The per-category keys are then flipped off the same way. What this cannot do — verified against the live settings tree — is suppress the security email-change alert to the old address: Pinterest hard-scopes those out of the switch (“Pinterest will always send you important updates about your account”) and no account-email toggle exists in the tree. The victim's one lifeline is that single alert; everything else goes quiet.

POST https://ask.pinterest.com/api/proxy/pinterest/settings/email/  section=settings_email_everything & option=ONLY_REQUIRED & value=true

What the attacker holds after one page visit

  • The account email is the attacker's plus-address (step 4–5): a fresh bughunter333333+<random>@gmail.com per run, all folding into bughunter333333@gmail.com. Every future account email is attacker-owned.
  • A password reset already dispatched to that mailbox (step 6): following the link and setting a password finishes the takeover and logs the victim out.
  • The MFA backup codes (step 7): one-time second factors, minted and stolen without any re-authentication.
  • The full session inventory (step 8): devices, IPs and geolocation, with a per-session revocation primitive to evict the victim silently.
  • Optional email notifications disabled first (step 3): the account is switched to only-required mail with no prompt, so almost every email the account would send goes quiet. The security change-of-email alert itself is not suppressible — verified against the settings surface — and remains the victim's only signal.
Authorized demonstration against the operator's own test accounts. Root cause: ask.pinterest.com/api/proxy/pinterest/* forwards v3 gateway reads and writes with the victim's session cookies and no CSRF defense — no token, no Origin or Referer check, form posts accepted. Pinterest session cookies are SameSite=None so they ride along on cross-site requests; when a browser blocks them in embedded contexts the same form is submitted as a top-level navigation and the cookie is attached there instead. The www.pinterest.com relay demands an X-CSRFToken header for these operations; the ask proxy skips that layer entirely.
