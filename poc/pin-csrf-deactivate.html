Cross-site account deactivation of a logged-in Pinterest user via the ask.pinterest.com proxy

This page is hosted on a completely different website (akashsebastian.com) from the victim's Pinterest session. While you are logged in to Pinterest in this browser, it destroys your account with a single cross-site form POST. No password, no prompt, no Pinterest tab open. It first confirms you are logged in (read side of the same proxy), then fires the write. Open DevTools and watch the requests leave this page for Pinterest's servers.

Safety interlock (not part of the exploit)

This hosted copy requires one manual click so that a stray visitor cannot destroy a real account by accident. The attacker version submits the form automatically on page load. Everything else here, the form, the target, the request, is exactly what the attacker page does.

Confirm the victim is logged in (read side)

The page checks that a Pinterest session exists in this browser before striking. A script tag pointed at the proxy wraps the response in a callback, so this foreign page can read your account data. Same bug family, read half.

Fire the cross-site POST that deactivates the account (write side)

An ordinary HTML form POSTs to the proxy endpoint, aimed at a hidden iframe. The browser attaches your Pinterest cookies automatically because they are SameSite=None. This is a CORS simple request: no preflight, no CSRF token, nothing for Pinterest's defenses to see. The proxy executes v3_deactivate_user with your session.

POST https://ask.pinterest.com/api/proxy/pinterest/users/me/  first_name=Stag

The form submits into a hidden iframe. The response is cross-origin so this page cannot read it, but the next step proves what it did.

The account that was live seconds ago no longer exists. One visit to an attacker page did this. The victim sees no warning and gets no confirmation dialog. Their pins, boards and profile are gone.

Demonstration against my own test account. The attacker version auto-submits on load; this hosted copy has a manual interlock. Root cause: ask.pinterest.com/api/proxy/pinterest/* forwards v3 gateway writes with the victim's session cookies and no CSRF defense, no token, no Origin or Referer check, any content type. Pinterest session cookies are SameSite=None so they ride along on cross-site POSTs. The www.pinterest.com relay requires an X-CSRFToken header for the same operation; the ask proxy skips that layer entirely.
