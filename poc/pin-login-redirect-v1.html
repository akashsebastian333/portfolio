Post-login open redirect and Apple OAuth login-CSRF

One link. no victim click beyond the link no CSRF token

Two chained flaws in the login flow. (1) The ?next= post-login redirect is taken from the raw query string and passed straight to window.location.href — and the URL-origin allowlist is explicitly bypassed on desktop ({disableOriginCheck:!0}), so after ANY successful login the victim's authenticated browser lands on an attacker-controlled page. (2) The Apple Sign-In callback (/oauth/login#id_token=…) auto-submits the token with no state and no nonce check — Apple requires a nonce for id_token flows — so an attacker can log the victim into the attacker's own account (session-riding) or link the attacker's Apple ID to the victim's account (persistent backdoor). Combined: the victim is moved to attacker content immediately after authenticating, which is exactly the window the ask-proxy CSRF family needs.

1The post-login redirect (trigger link)

Send the victim this link. The webapp stores next verbatim (search.split("?next=")[1] — no validation), and after login resolves it through a helper that passes absolute URLs through unchanged before assigning window.location.href. The safety check lives in a wrapper that is invoked with disableOriginCheck:!0 on desktop.

LINK https://www.pinterest.com/login/?next=…

2Apple login-CSRF (no state, no nonce)

The authorize request carries neither state nor nonce despite requesting id_token. The callback reads the token straight out of the URL fragment and posts it — nothing is compared to anything Apple returns. The only stored value is the post-login redirect path. Drive it with the attacker's own Apple code and the victim is silently authenticated as the attacker (or the attacker's Apple ID is linked to the victim's account).

LINK https://www.pinterest.com/oauth/login#id_token=<attacker-token>
